The `Project` ↔ `Repository` link is many-to-many (`server/prisma/schema.prisma:42-101`), and bounties reference `repositoryId` (`:113-130`). `AddCommunityRepositoryUseCase` caps a community at 10 linked repos (`server/src/modules/community/application/add-community-repository.usecase.ts:26-36`). The contributor index stores `githubId`, `contributions`, generation, and sync metadata (`schema.prisma:992-1017`), but the published participation response does **not** expose those per-repo numbers. Even if exposed, summing them would not establish unique commit SHAs across forks, mirrors, and linked repos. The current SQL uses `contributions>0` and groups by GitHub ID (`prisma-project-participation.ts:11-76`).

Existing mutation endpoints such as `POST /api/community/projects`, `POST /api/community/projects/:id/repos`, and `POST /api/bounties` require their own actor/payment rules and are **outside LootTown**. The community routes use a community cookie guard; bounty claim uses bearer wallet authentication (`community-publication.controller.ts:91-131`, `bounties.controller.ts:165-225`). The product's GitHub authorization inventory is `docs/features/github-authorization.md` in DevLoot. Its L0–L5 levels are proposed independent capability bundles, not evidence of live grants. LootTown requires no GitHub token for the offline base and must not silently expand permissions.

## Proposed LootTown projection v1 — not implemented in DevLoot

The browser schema lives in `src/contracts/venue.ts`; the only adapter today is the synthetic `src/demo.ts` fixture. A future DevLoot read endpoint or same-origin server projection should expose one venue per community with `{schemaVersion:1,community:{id,name},coverage:{complete,lastSyncedAt,policyVersion},people:[{githubId,handle,communityCommitCount,eligible}]}`. `communityCommitCount` is `number|null` in **unique attributed commits**, not repo contributions or bounties. Incomplete coverage must use null counts. The backend must define exclusion and deduplication policy, stable identity, repository set, source window, freshness, and pagination/snapshot consistency. The first release should not display a definitive venue scale while coverage is incomplete. `src/contracts/venue.ts` validates the version and rejects conflicting duplicate person aggregates; it does not manufacture missing data.

Proposed UI integration callbacks, not HTTP routes: `selectCommunity({communityId})`, `selectPerson({communityId,githubId})`, `openBounty({bountyId})`. DevLoot owns URLs, login, permissions, and payout. The standalone adapter needs an actual public CORS policy for its origin; an embedded same-origin component should use the host's existing fetch/navigation context. Do not set browser `Access-Control-Allow-Origin` headers and claim CORS solved. No production writes are needed.
